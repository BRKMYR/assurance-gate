Assurance Gate

Evaluation results in, release decision out. Gates are written down and frozen before the run. Each one reports a confidence bound next to its threshold, and the dashboard carries the evidence for every number it shows.

Live · pre registered holdout suite · two tracks

At a glance

What

Assurance Gate turns test results into a release decision. It reads the results for a candidate system, checks them against thresholds that were written down and hashed before the run, and returns GO, NO GO or CONDITIONAL. Two tracks share one engine: driving planners in a simulator, and open language models on safety benchmarks.

Why it matters

A benchmark score is not a decision. Teams move thresholds after they see the numbers, and they read a rate from sixteen runs as if it were certain. This tool makes both habits visible. The threshold exists before the result, and every rate carries a confidence bound, the range the true rate could fall in.

How it was built

I wrote the specification, the twelve gate thresholds with their rationales, and the owner texts by hand. Claude Code agents implemented the Python engine, two result adapters and the static dashboard from that specification in one day. 138 tests, a byte identical build and a copy linter run on every push.

Problem

A score is not a release decision.

Every benchmark I have built ends in a number, and the number was never the hard part. The hard part is the release meeting: is this good enough, against which threshold, decided when, by whom. If the threshold is set after the run, the answer is worthless. This project makes the meeting a page and forces the threshold to exist first.

Two habits make an evaluation score unusable as a decision. Thresholds move after the numbers are known, and a rate from a small sample is read as though it were certain. Both are invisible in the final slide.

What it does

One folder of results in, one verdict with evidence out.

The tool takes a folder of evaluation records and a gate file and produces one verdict per candidate with the evidence under it. The gate file is frozen and its hash is published on GitHub and on a Hugging Face dataset before any run starts. Each run manifest records both timestamps. The engine evaluates every gate, checks coverage and regression, builds an assurance case tree and writes a static dashboard.

  • Refuses to pre register a gate file that still holds a placeholder or is not marked frozen, and refuses when a run for that suite already exists. preregister.py
  • Decides every rate gate on the exact two sided 95 percent Clopper Pearson bound, computed without external libraries so the number is identical on every machine. stats.py, engine.py
  • Marks a gate as insufficient when scorable records fall below its minimum sample size, and marks a whole suite as not pre registered when gates were written after the run. engine.py, ingest.py
  • Fails coverage on any parameter bin or hazard category with zero records, and fails regression on any scenario that got worse against the baseline even when the average improved. coverage.py, regression.py
  • Writes the same bytes for the same inputs, and strips paths, host names and addresses from every published file. build.py, sanitise.py

Solution

Freeze the gates, publish the hash, then run.

A gate file holds every threshold with its rationale and its source. The file is hashed, the hash is published, and the run manifest records both timestamps. A reader can see whether the gates existed before the result did.

Each rate gate passes on a Clopper Pearson bound rather than on the point estimate, so a small sample cannot buy a pass. Count gates on collisions stay absolute. Coverage checks that every parameter bin was drawn at all. A paired regression compares the candidate against its baseline scenario by scenario. The verdict is GO, NO GO or CONDITIONAL, and a waiver can only soften a soft gate, never a hard one.

Two tracks share the engine. Track A reads driving scenario runs from a simulation suite. Track B reads language model safety evals produced with Inspect.

Result

One verdict, with the evidence under it.

On the pre registered holdout suite all three baseline planners are NO GO. The cautious planner fails 2 of 9 gates, the plain car following planner 3 of 9, the constant velocity planner 6 of 9. For the car following planner, 11 of 16 occluded pedestrian scenarios end in a collision, so the hard gate fires before any margin matters. Its cut in gate passes on the point estimate (12 of 14) and fails on the 95 percent lower bound (0.572 against a floor of 0.60). That gap is why the bound is the rule.

Track B ran three open language models against pre registered ceilings on harmful compliance and over refusal, 763 prompts each. One model answers 1 of 310 unsafe prompts and passes that ceiling, then declines 26 of 248 safe prompts and fails the other. All three models are NO GO.

Why it matters

A stranger can reproduce the decision.

The gate file hash sits in a GitHub release and a dataset commit stamped 20:18 UTC, the first holdout run is stamped 20:19, and every number on the dashboard links to the record behind it. The project also shows the cost of ignoring sample size: a planner clears the cut in gate on its point estimate and fails it on the bound. And it shows that one gate model fits a driving planner and a language model alike, since Track B ran three open models against the same kind of frozen ceiling.

In five years

Evaluation results for safety relevant AI will be filed the way clinical trial results are filed: thresholds registered before the run, records public, verdict recomputable by anyone. Regulators under the EU AI Act and ISO/PAS 8800, the road vehicle AI safety standard, will ask for exactly this evidence layer. This project is a small early version of that filing format, built by one person for two suites.

Success criteria

When this counts as working.

  • The gates for a run were frozen and published before that run started, and the dashboard shows both times.
  • Every rate gate reports a bound next to its point estimate, and the bound is what decides.
  • Coverage names every empty bin, and an empty bin blocks the release on its own.
  • A regression against the baseline catches any scenario that got worse, even when the average improved.
  • Nothing private reaches a published file. No raw trajectory log, no local path, no address.
  • A reader The dashboard is built so a reader reaches the evidence behind a failing gate in three taps on a phone.
  • The build is deterministic. The same inputs produce the same bytes.
  • Every judgement call in the build is written down where a reviewer can find it.

Metrics, KPIs, evals

What the dashboard reports.

MetricTypeWhat it tells the PM
Verdict GO, NO GO, CONDITIONAL The release call for one candidate against one frozen gate file. CONDITIONAL means a soft gate failed and a waiver with a named signer and an expiry carries it.
Gates failed of n count How much of the gate set is red, and which classes. Hard gates rank first, then severity, so the first row is the one to fix.
Coverage empty bins count Parameter ranges the suite never drew. An empty bin means the claim was never tested there, and it blocks the release.
Regression drops count of pairs Scenarios where the candidate got worse than the baseline by tier or by time to collision. A better average still fails here.
Bound example rate and bound Thirteen passes out of sixteen give a point estimate of 0.8125 and a lower bound of 0.5435. A floor of 0.60 fails on the bound.
What this does not do.
  • It does not replace a safety case. It produces the evidence layer one would sit on.
  • A gate can only see what the suite tested. The limitations page lists the hazards no gate covers.
  • Demo runs are labelled as demo. Their gates were written after the fact, and the dashboard says so.
  • The gates, the scenarios and the planners were written by the same person, one minute apart. The dashboard names this as a live weakness.
  • On Track B one hazard category has zero prompts in both benchmarks as mapped, so the coverage gate fails every model. Whether that is a benchmark gap or a mapping error is an open item.
